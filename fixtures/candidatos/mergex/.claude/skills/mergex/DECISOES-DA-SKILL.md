# Decisões tomadas na construção da skill mergex

Ambiguidades do prompt de especificação resolvidas pela opção mais conservadora, uma linha de contexto cada.

| # | Ambiguidade | Decisão tomada | Motivo |
|---|---|---|---|
| DM-01 | O prompt descreve nove blocos (E0–E8 mais o comando manual), mas nunca dá um número à etapa de revisão, e a árvore pede `09-revisao.md` | A revisão é a **etapa E9**, nomeada assim em toda a skill | A árvore já numera o reference como `09`; deixar a etapa sem número tornaria as tabelas e as regras ambíguas |
| DM-02 | Colisão de nomes: os estágios da runx são E1–E5 e as etapas da mergex são E0–E9 — "E3" significa duas coisas | Toda menção diz de qual skill é o estágio ("E3 da runx", "E3 da mergex"), e o `integracao/runx.md` abre com o aviso da colisão | Um agente lendo "aciona no E3" sem qualificação erraria o ponto de acionamento em metade dos casos |
| DM-03 | O prompt não define onde ficam `PR.md` e `ATENCAO.md` — só cita `ENTREGA.md` e `QA-PACOTE.md` em `docs/entregas/<trabalho_id>/` | Os quatro arquivos ficam na mesma pasta `docs/entregas/<trabalho_id>/` | É a única pasta de entrega que o prompt define; espalhar artefatos da mesma entrega quebraria os links relativos entre eles |
| DM-04 | O prompt manda gravar `PR.md` quando a ferramenta de PR está ausente, mas não diz se ele é gravado quando o PR abre normalmente | `PR.md` é gravado **sempre**, no E4, antes do E7 | O arquivo é o registro da entrega; o PR no serviço é a cópia dele. Gravar só na falha deixaria a entrega sem registro no caminho feliz |
| DM-05 | O prompt lista dez itens do portão em prosa corrida, sem identificadores | Numerados **V1 a V10**, e todos aparecem sempre na tabela de saída, inclusive os `n/a` | Sem identificador não há como a saída dizer "V2 falhou"; marcar `n/a` em vez de omitir distingue "não se aplica" de "esqueceram de verificar" |
| DM-06 | O portão barra por "QA.md do runx reprovado", mas o prompt não diz o que barra num trabalho da sprintx, que não tem QA | V5 (QA) é `n/a` na sprintx, e foi criada a **V6 — auditoria da sprintx reprovada**, derivada de "F5 auditoria reprovada faz E2 barrar" | A regra existe no prompt (seção de integração), mas não estava na lista das dez; sem V6 a auditoria reprovada não teria onde barrar |
| DM-07 | Os critérios das três faixas são listados em prosa, sem identificadores | Numerados **O1–O8, L1–L3, D1–D3**, e toda justificativa tem que nomear pelo menos um | A regra 8 exige classificação derivada de evidência; sem identificador, "por quê" vira prosa e a auditoria da classificação fica impossível |
| DM-08 | O prompt não diz o que fazer com arquivo do diff que não bate em nenhum critério de nenhuma faixa | Vai para **OLHO OBRIGATÓRIO por padrão**, com a razão declarada ("sem evidência de cobertura; classificado no padrão") | "Na dúvida, sobe para a mais rigorosa" é a regra dura; ausência de evidência é ausência de prova, não prova de segurança |
| DM-09 | O prompt não diz como classificar arquivo **removido** (`D` no diff) | Classificado pelo que ele era; **teste removido nunca é DISPENSÁVEL** — é perda de cobertura, logo OLHO OBRIGATÓRIO | D1 fala de teste que "só acrescenta caso"; um teste apagado é o oposto disso, e é exatamente onde um bug entra sem ninguém ver |
| DM-10 | O critério D3 dispensa "arquivo gerado automaticamente, quando declarado como tal", mas migrações de ORM também são geradas | **Migração de banco é sempre O3**, mesmo gerada; D3 só vale para arquivo gerado que *reflete* algo já revisado e não tem efeito próprio | O prompt manda migração de banco ser OLHO OBRIGATÓRIO ("qualquer uma", regra 9); a exceção de arquivo gerado não pode engolir uma regra inviolável |
| DM-11 | O prompt não define o que conta como "declarado como tal" para arquivo gerado | Declaração no `CONVENCOES.md` da stackx, cabeçalho "generated by" no próprio arquivo, ou `linguist-generated` no `.gitattributes`. **Sem declaração, não é tratado como gerado** | Assumir que algo é gerado porque parece gerado é classificação por sensação, e viola a regra 8 |
| DM-12 | O prompt define o formato da mensagem de commit, mas não diz o que fazer quando a task não tem escopo evidente | Omitir os parênteses: `fix: <título>` | É a forma canônica quando não há escopo; inventar um escopo seria gerar conteúdo novo (regra 7) |
| DM-13 | O prompt manda "nunca commitar arquivo fora da lista declarada", mas não diz o que fazer com o arquivo que ficou de fora | Não entra no commit, não é apagado, fica na árvore, e é registrado em `desvios` no `ENTREGA.md`; a V9 do portão barra depois, nomeando-o | Apagar seria descartar trabalho de alguém (proibido); commitar violaria a regra 4; barrar depois devolve a decisão para a pessoa |
| DM-14 | O prompt não diz como adicionar arquivos ao commit | Por caminho explícito, nunca `git add .`, `-A` ou `-u` | Os atalhos arrastam o que não foi declarado, o que violaria a regra 4 silenciosamente |
| DM-15 | O prompt manda varrer segredo mas não define os sinais nem o que é falso positivo | Tabela de quatro categorias (chave de API, credencial, chave privada, dado real de cliente) com sinais concretos; placeholder óbvio não é segredo; **na dúvida, trata como segredo** | Sem critério concreto a varredura vira sensação; a assimetria (na dúvida, barra) é a única segura para um falso negativo que vaza credencial |
| DM-16 | O prompt não diz se o valor do segredo encontrado aparece na mensagem de aviso | **Sempre mascarado** (`sk-...4f2a`), nunca ecoado em saída, log ou arquivo | Ecoar o segredo no relatório o espalharia para mais um lugar, que é o oposto do objetivo da verificação |
| DM-17 | O prompt não define a estratégia de detecção de "commits no remoto que a branch local não tem" | `git fetch` seguido de `git rev-list --count HEAD..origin/<branch>`; contagem maior que zero para e avisa | É a checagem que não altera nada da árvore; qualquer forma de reconciliar violaria "para e avisa em vez de reconciliar" |
| DM-18 | O prompt manda o E9 analisar conflitos, mas analisar exigiria tentar o merge | `git merge-tree` sobre a base de fusão, que calcula o conflito **sem tocar na árvore de trabalho e sem criar commit** | Fazer um merge de verdade "só para ver" deixaria estado sujo e poderia disparar um merge não confirmado |
| DM-19 | O prompt dá seis fatores para ordenar por impacto no E9, mas não a precedência entre eles | Ordem lexicográfica declarada: raio → arquivos em olho obrigatório → sobreposição → conflito → quantidade de arquivos → número do PR (desempate estável) | Sem precedência a ordenação não é reproduzível; o número do PR ao fim garante ordem estável entre PRs equivalentes |
| DM-20 | O prompt manda ordenar do menor para o maior impacto, mas não diz onde ficam os PRs inelegíveis (rascunho, CI vermelha) | Aparecem na lista, **no fim**, marcados com o motivo, e não entram na condução | Omiti-los esconderia trabalho aberto; oferecê-los violaria as recusas duras |
| DM-21 | O prompt não diz o que fazer quando `mergeable` do PR é desconhecido | Verifica localmente com `merge-tree`; se não for possível, marca "conflito não verificado" e **trata como conflito** | Conservador: tratar conflito desconhecido como ausente poderia oferecer para merge algo que quebra |
| DM-22 | O prompt define `pr_estado` com quatro valores mas não diz quando cada um é gravado, nem o valor antes de o PR existir | `rascunho` na abertura normal, `aberto` quando o QA já aprovou, `merged`/`fechado` atualizados depois; `null` enquanto não há PR | O contrato proíbe omitir chave; `null` é o valor de "não se aplica ainda" |
| DM-23 | O prompt não diz qual `expx_tool` o `ENTREGA.md` declara, já que a mergex não está no enum do schema v1 | `expx_tool` fica com a skill de **origem** (`sprintx`/`runx`) e foi acrescentado `entregue_por: mergex` | Mudar o enum de um contrato compartilhado quebraria o painel que lê as três skills; o campo novo é aditivo |
| DM-24 | O prompt não define os enums de `estado` e `portao` do `kind: entrega` | `estado`: `aberto`/`entregue`/`bloqueado`; `portao`: `pronto`/`bloqueado`/`null` | Derivados diretamente dos estados que o prompt descreve em prosa (E0 abre, E2 barra, E8 fecha) |
| DM-25 | O prompt não diz se o `ENTREGA.md` de um trabalho barrado no portão fica `bloqueado` ou `entregue` | `estado: bloqueado` e `portao: bloqueado`; o resto fica `null`/`false` | O painel precisa distinguir o que aguarda revisão do que travou; marcar como entregue algo barrado seria maquiar |
| DM-26 | O E0 exige árvore limpa, mas o prompt não diz se arquivo apenas **não rastreado** (`??`) conta | Conta. Qualquer linha de `git status --porcelain` para o E0 | Pode ser trabalho de alguém; a skill não julga o conteúdo do que não é dela |
| DM-27 | O prompt manda o E6 rodar "depois de E2 aprovar e do pacote de QA existir", mas não diz o que fazer sem remoto configurado | `push_feito: false`, informa que o trabalho está commitado localmente, e segue para o E8 sem erro | Mesma lógica da regra 12 (ferramenta ausente não é erro): a entrega local continua válida |
| DM-28 | O prompt manda abrir o PR "como rascunho quando o pacote de QA ainda não foi aprovado", mas o fluxo normal entrega antes do QA rodar | **Rascunho é o padrão**; pronto para revisão só com `VEREDITO: APROVADO` no `QA.md` | É o estado honesto no fluxo normal, e o E9 nunca faz merge de rascunho — o que fecha o ciclo |
| DM-29 | O prompt não diz se a mergex adiciona revisor, etiqueta ou responsável ao abrir o PR | Não adiciona nada por conta própria; só o que o `CONVENCOES.md` da stackx declarar | Escolher destinatário sem artefato que o sustente seria gerar conteúdo novo (regra 7) |
| DM-30 | O prompt manda a descrição do PR "caber em uma tela", o que conflita com "lista de arquivos completa" num diff grande | A lista de arquivos e a seção "onde eu quero seu olho" **nunca são cortadas**; corta-se prosa. Proibido resumir com "e mais N arquivos" | As duas seções são a razão de a skill existir (perceber sobreposição e saber onde olhar); o arquivo omitido seria justamente o que colide |
| DM-31 | O prompt não diz onde ancorar `docs/entregas/` em monorepo | Raiz do repositório mais próxima (a que contém `.git/`); sem `.git` em nenhum ancestral, a raiz do diretório de trabalho; reaproveitar `docs/` existente | Mesma regra que a sprintx e a runx já usam para `docs/`, mantendo as três árvores no mesmo lugar |
| DM-32 | O prompt não diz o que o E5 faz quando não existe roteiro de teste manual (trabalho da sprintx, que não tem `QA.md`) | Deriva os casos dos `criterio_aceite` das tasks, traduzidos para linguagem de tela, e registra o aviso de que o roteiro original não existia | Traduzir critério existente é costura (permitida); inventar caso de teste seria conteúdo novo (regra 7) |
| DM-33 | O prompt manda o pacote de QA apontar o relatório de uso da runx, que ainda não existe quando a mergex entrega | Aponta o caminho onde ele vai ficar e **diz explicitamente que ainda não existe** | O E5 da runx roda depois da entrega aceita (regra 19); apontar para um arquivo inexistente sem avisar confundiria o QA |
| DM-34 | O prompt não diz se a mergex pode escrever no `ORQUESTRADOR.md`, que é artefato das irmãs | Escreve **uma única linha**, registrando a branch, e nada mais | O prompt manda registrar a branch ali; limitar a escrita a essa linha preserva a propriedade do artefato pela skill de origem |
| DM-35 | Idioma dos arquivos da skill | Todo o conteúdo em pt-BR, inclusive a `description` do frontmatter | Prompt, marca, ecossistema e usuário são pt-BR, como na sprintx e na runx |
| DM-36 | Marcadores de preenchimento nos templates | Padrão `{{assim}}` em todos os assets, com nota no topo mandando substituir tudo e apagar o cabeçalho | Mesmo padrão da sprintx (DS-13), fácil de grepar por vazamento |
| DM-37 | O prompt manda a `legadox` alimentar o portão e a classificação, mas ela não está instalada nem tem formato de artefato publicado | Os references consomem os artefatos por **descrição funcional** (raio, zonas, caracterização, reversão), e o `patch-legadox.md` é quem define o formato estável (`FAIXA: ALTO`, tabela de zonas com caminhos) | Sem o patch aplicado, a mergex trata tudo como fonte ausente e segue; com ele, casa caminho de arquivo com zona de risco |
| DM-38 | O prompt não define o que é `PROPOSTA` no `CONVENCOES.md` além de "não governa" | Três estados explícitos: `OBSERVADO` governa, `PROPOSTA` vira aviso, `NAO DETERMINADO` deixa a mergex usar o próprio padrão | Sem os três estados nomeados, "não governa" não teria como ser verificado por outra skill |
| DM-39 | O prompt não diz o que fazer quando o `CONVENCOES.md` declara uma convenção que o repositório não pratica | Segue o `CONVENCOES.md` (é a decisão declarada do time) e registra a divergência como **aviso** | Convenção declarada vence detecção; a divergência é informação útil, mas nunca barra — o portão barra por trabalho incompleto, não por estilo |
| DM-40 | O prompt exige a description de `mergex-revisar` "estrita e não convidativa", sem dizer como impedir o disparo automático na prática | Description escrita em negativa explícita (não use por iniciativa própria, não encadeie, não ofereça ao fim de um trabalho) e reforçada no corpo do comando, no `09-revisao.md`, no `08-registro.md`, no `AGENTS.md` e nos quatro patches | Uma description apenas "estrita" ainda dispararia por similaridade semântica; a negativa explícita em todos os pontos de contato é o que efetivamente impede o encadeamento |

## Decisões da implementação de hooks e agentes

| # | Ambiguidade | Decisão tomada | Motivo |
|---|---|---|---|
| DM-43 | O contrato manda o hook "sempre gravar no rastro, inclusive quando permite", mas o vocabulário de `evento` não tem termo para "avaliou e deixou passar" | A passagem limpa é **silenciosa**; nenhum enum novo foi inventado. Lacuna registrada em `hooks/README.md` para o dono do contrato | `evento` é lista fechada lida pelo painel; inventar um valor quebraria a leitura. O propósito declarado (a lista que guia a promoção de aviso para bloqueio) é atendido só com `regra_violada` e `acao_bloqueada` |
| DM-44 | O rastro é gravado em `docs/eventos/`, dentro da árvore de trabalho, e o `branch-limpa` conta arquivo não rastreado como pendência | Os hooks criam `docs/eventos/.gitignore` com `*` na primeira gravação | Sem isso o próprio rastro sujaria a árvore e o `branch-limpa` passaria a barrar **toda** troca de branch. O ignore fica dentro da pasta do rastro para não tocar o `.gitignore` do projeto, que é do time |
| DM-45 | Como identificar o `trabalho_id` corrente dentro de um hook, que não pode ter estado próprio | O `ENTREGA.md` mais recentemente modificado em `docs/entregas/*/` | Regra 6 do contrato: toda decisão sai de arquivo que já existe. O `ENTREGA.md` é o registro que o E0 cria e o E1 atualiza a cada commit |
| DM-46 | O `git-perigoso` barra reescrita de histórico, mas rebase e amend locais são trabalho legítimo | Só barra quando **todos** os commits da branch já estão no remoto (`rev-list --count <upstream>..HEAD` igual a zero) | Reescrever o que ainda é local não afeta ninguém. Barrar isso seria o falso positivo que faz o time desligar o hook — e junto com ele os de segurança |
| DM-47 | O `pr-so-com-portao` roda em todo `git push`, inclusive em repositório sem trabalho da mergex | Sem `ENTREGA.md`, o hook não é acionado | Precisão (regra 1 do desenho): o hook intercepta toda chamada de terminal, e push de outra coisa não pode ser atrapalhado |
| DM-48 | O `revisor-diff` precisa rodar `git diff`, o que exige `Bash` — ferramenta que também escreve | `revisor-diff` recebe `Bash`; o `analista-de-conflito`, que é quem precisa da garantia mecânica de não resolver conflito, recebe **só** `Read`, `Grep` e `Glob` | A garantia forte vai onde ela é o ponto: o CLAUDE.md pede que seja "mecanicamente" impossível o analista resolver conflito. O `revisor-diff` classifica, não altera, e o diff exige o versionador |
| DM-49 | O `commit-por-task` compara o que está em stage com os arquivos declarados; o formato real do `tasks.md` usa lista de fluxo (`cria: [a.ts, b.ts]`), não lista em bloco | O leitor aceita **as duas formas** | O formato real do `expx-schema v1`, conferido nos `tasks.md` existentes, é o de fluxo. Um leitor que só entendesse a forma em bloco não acharia arquivo nenhum e o hook viraria um no-op silencioso |
| DM-50 | Linguagem dos hooks, dado o orçamento de 200 ms por chamada de terminal | `bash` + `jq`, com saída antecipada quando o comando não é do versionador | Medido: ~22 ms no caso comum (comando que nem toca git) e ~131 ms no caminho pesado. Um interpretador maior começaria em ~44 ms só de partida, antes de qualquer trabalho |
| DM-51 | Os scripts precisam rodar no bash do macOS, que é a versão 3.2 | Nada de `mapfile`/`readarray` nem construções de bash 4+ | `mapfile` falha silenciosamente no bash 3.2: o hook não quebra (falha aberta), mas deixa de verificar qualquer coisa — o pior dos dois mundos |
| DM-52 | O `arquivo-fora-do-plano` compara o stage com o plano, mas a própria mergex grava `ENTREGA.md`, `PR.md`, `ATENCAO.md` e `QA-PACOTE.md`, que nenhuma task declara | `docs/entregas/` e `docs/eventos/` são isentos | São a saída da entrega, não o trabalho planejado. Sem a isenção, todo commit de artefato da mergex viraria aviso de escopo |
| DM-53 | Onde os hooks e agentes moram: o contrato descreve uma árvore `plugin/` (hooks/, agents/, skills/), mas este repositório entrega a skill por `.claude/` e `.opencode/` | Seguem a convenção do repositório: `.claude/hooks/`, `.claude/agents/`, `.opencode/plugin/`, `.opencode/agent/` — a mesma que a `stackx` e a `sprintx` já usam | Regra 14: convenção do repositório vence a convenção padrão. A árvore `plugin/` do contrato descreve como o CLI **empacota**, não como cada repositório de skill se organiza |
| DM-54 | O `.expx/hooks.json` do contrato aparece como `{"modos": {"<nome>": "aviso"}}`, mas as skills irmãs já gravam `{"hooks": {"<nome>": {"modo": "aviso"}}}` | O leitor aceita **as duas formas**, preferindo a das irmãs | Divergir do que já está escrito em disco criaria dois formatos no mesmo ecossistema. Aceitar a forma antiga evita quebrar arquivo já editado à mão |
| DM-55 | O OpenCode não tem hooks de configuração: só plugin JS/TS, e o `tool.execute.before` não tem "permite mas avisa" — ou passa em silêncio, ou lança | O plugin **invoca os mesmos scripts** de `.claude/hooks/`; o aviso é represado no `before` e anexado ao resultado da ferramenta no `after` | Duplicar a lógica criaria duas fontes divergindo com o tempo — o pior defeito para uma skill cujo contrato é o produto. A ponte tem só o registro, que é o que de fato difere |
| DM-56 | O Claude Code lê o aviso do hook no stderr; a ponte do OpenCode lê JSON no stdout | Os hooks emitem o aviso **nos dois canais** | Emitir só no stderr faria todo aviso se perder no OpenCode, silenciosamente. Cada harness ignora o canal do outro, então não há ruído |
| DM-57 | O `analista-de-conflito` no OpenCode, cujo formato de agente usa booleanos por ferramenta | `bash: false`, além de `write: false` e `edit: false` | A garantia de que ele não resolve conflito precisa ser mecânica **nos dois harnesses**, não só no Claude Code |
| DM-58 | O hook de descarte casava `git restore` sem distinguir as opcoes, e barrou um `--staged` legitimo em uso real | So e descarte quando mexe na arvore: `--staged` sozinho passa; sem opcao, ou com `--worktree`, barra | `--staged` apenas desfaz o stage e nao destroi nada. Barra-lo e o falso positivo que o desenho manda evitar — quatro casos de regressao entraram na suite |

## Decisões da integração com o memox

| # | Ambiguidade | Decisão tomada | Motivo |
|---|---|---|---|
| DM-59 | O prompt manda acrescentar campos "no kind entrega do `00-schema.md`", mas a mergex não tinha esse arquivo — o contrato do `kind: entrega` vivia dentro de `references/08-registro.md` | Criado `references/00-schema.md`, com o contrato completo do kind; o `08-registro.md` mantém o que se precisa para gravar e aponta para ele | As irmãs têm o contrato num `00-schema.md` próprio; deixar o da mergex embutido na etapa faria o único documento de contrato do ecossistema ter três formatos. Nenhuma regra do `08-registro.md` foi removida |
| DM-60 | O prompt pede o campo `faixa_por_arquivo`; o motor do memox (`memox.py`, linha 618) lê `faixa_atencao`, e é o nome que o `patch-mergex.md` do próprio memox exige | Gravado como **`faixa_atencao`**, com a forma `{arquivo, faixa}` que o prompt descreve | O prompt manda corrigir divergência de nome que quebre o índice. `faixa_por_arquivo` não seria lido por ninguém: o campo existiria e o sinal `faixa_atencao_frequente` continuaria vazio para sempre |
| DM-61 | As três faixas da mergex têm nome em prosa (OLHO OBRIGATÓRIO, LEITURA RÁPIDA, DISPENSÁVEL); o índice do memox usa `alta`/`media`/`baixa` | Mapeamento fixo e declarado: OLHO OBRIGATÓRIO → `alta`, LEITURA RÁPIDA → `media`, DISPENSÁVEL → `baixa`. O YAML leva o vocabulário do índice; a prosa e o `ATENCAO.md` seguem com os nomes de sempre | O painel e o índice leem o YAML; a pessoa lê a prosa. Gravar "OLHO OBRIGATÓRIO" no campo faria `faixa_atencao_frequente` devolver uma string que nenhuma outra skill reconhece |
| DM-62 | O prompt diz que `arquivos_alterados` é "o diff real, não a previsão do plano", mas o campo de mesmo nome na sprintx e na runx **é** a união das tasks | Mesmo nome, semânticas declaradamente diferentes, com a diferença escrita no `00-schema.md`; a divergência entre o diff e o plano continua indo para `desvios` | Renomear na mergex quebraria a consulta única do índice, que é o ponto do campo. sprintx e já foi corrigida lá. A outra é desta skill: `docs/sprintx/estimativas/HISTORICO.md`
aparecia como arquivo de produto fora do plano. A sprintx (0dddbfa) declarou formalmente o dono
do arquivo; o que faltava aqui era consumir essa declaração — e, junto dela, o formato de sprint
condensada que a skill irmã formalizou.

| # | Ambiguidade | Decisão tomada | Motivo |
|---|---|---|---|
| DM-101 | `HISTORICO.md` é método, mas mora **fora** da pasta da feature — e a isenção de método da mergex era por pasta do trabalho | Exceção **exata**: o caminho literal `docs/sprintx/estimativas/HISTORICO.md`, e **somente quando a origem é a sprintx**. Nada sob `docs/sprintx/estimativas/**`, nada sob `docs/sprintx/**`, nada equivalente na runx. runx declarar um artefato global equivalente — que precisaria de contrato próprio, porque esta
isenção é da sprintx e não se estende por analogia.

## P1 — atenção humana dos artefatos de método (E3)

O segundo E2E real (buildx → sprintx → mergex) passou inteiro, mas o E3 deu 17 arquivos em OLHO
OBRIGATÓRIO de 18 nas duas features, e 15 deles vinham só do padrão: plano, decisões, base,

## P0.2-A4 — o portão registra as falhas e o E8 deriva a causa

O `ENTREGA.md` terminal dizia **que** o portão barrou (`estado: bloqueado`, `portao: bloqueado`),
mas não **por quê**: o motivo ficava na prosa e na memória da sessão. No piloto, um bloqueio com
V1 e V7 (o B-01 pedia alterar arquivo fora do ownership) foi chamado à mão de `falha_tecnica` —
classificação que nenhum artefato sustentava. A buildx precisa ler a causa por `git show` no HEAD
da feature, sem interpretar texto.

| # | Ambiguidade | Decisão tomada | Motivo |
|---|---|---|---|
| DM-111 | Qual enum de `causa`, sem inventar por intuição | **Uma causa por verificação do portão** (V1–V10), e nenhuma outra. Cada valor passou as cinco perguntas: a mergex observa sozinha (é o resultado da própria verificação), é determinístico, duas execuções sobre a mesma evidência dão o mesmo valor, a evidência está commitada (`falhas_portao` no mesmo arquivo, e os artefatos lidos pelo E2 no histórico) e é causa do bloqueio **do ponto de vista do portão**. Classificações pelo conteúdo do bloqueio (`falha_tecnica`, `decisao_humana`, "fora do ownership") **não passam**: dependem de ler a narrativa do `B-NN`, que não tem campo tipado | A mergex é dona da causa observável do portão. Traduzir para classe de pendência é da buildx; classificar o `B-NN` pelo tipo exige que a sprintx o grave tipado |
| DM-112 | Como registrar as falhas | Chave nova **`falhas_portao`**, gravada pelo E2 junto com `portao`: as verificações com FALHA, na numeração do portão. Verificação que não pôde rodar entra como **`vN_sem_prova`** — o contrato já a marcava FALHA ("ausência de prova não é prova"), mas sem distingui-la de defeito provado | A causa precisa de evidência no mesmo arquivo para ser recomputável e auditável (`--validar` recalcula e compara). Sem o sufixo, um "não consegui verificar" seria lido depois como defeito provado |
| DM-113 | Várias falhas ao mesmo tempo | **Precedência fixa**: V10; depois V6–V9; depois V1–V5, cada grupo na numeração. A primeira presente decide. V10 primeiro pela regra 5. V6–V9 são fatos que existem independentemente de a execução ter terminado; V1–V5 leem o registro da execução, que fica incompleto justamente quando um daqueles fatos parou o trabalho (o contrato do E2 já diz que task `bloqueada` aponta o `B-NN`, e que QA ausente é fluxo que não chegou ao E4 da runx). Todas as falhas continuam em `falhas_portao` | Uma regra que qualquer leitor recalcula. A ordem não é juízo de gravidade; entre falhas independentes do mesmo grupo, a numeração é convenção declarada |
| DM-114 | Bloqueado sem causa determinável | Valor **`indeterminada`**, nunca `null` e nunca uma causa escolhida: quando a primeira verificação da ordem presente em `falhas_portao` é `_sem_prova`. Bloqueado com `falhas_portao: []` é registro inconsistente: o script recusa e o E2 roda de novo | A decisão de desenho pede bloqueado com causa não nula. `indeterminada` é a representação mínima disso, e quem lê a trata como causa não commitada |
| DM-115 | Quem grava `causa`, e quando | O **E8**, na mesma gravação de `estado: bloqueado` e antes do commit de fechamento, pelo script `scripts/causa-do-portao.sh --derivar`, validado com `--validar`. O E2 não grava causa: entre o E2 e o E8, `estado: aberto` tem `causa: null` | "Aberto → causa null" vale sempre. A causa entra no HEAD pelo mesmo commit que persiste estado, portão e push |
| DM-116 | `ENTREGA.md` anterior às chaves | **Leitura histórica aceita** (`--validar-historico` → `causa=ausente`: não commitada, nunca inferida); **gravação nova inválida** (`--validar` exige as duas chaves); **sem migração em massa** — a regra de migração existente acrescenta as chaves na próxima gravação, que só ocorre onde o valor é `null`/`[]` por definição. Bloqueio legado nunca ganha causa retroativa. Uma chave sem a outra reprova nos dois modos | Inferir a causa de um bloqueio antigo seria ler a prosa — exatamente o que este contrato proíbe |

**O caso do piloto.** `falhas_portao: [v1, v7]` → `causa: bloqueio_aberto`. O texto do B-01 não
muda o valor, e a mergex não o transforma em `falha_tecnica`. Distinguir "fora do ownership" de
outro tipo de bloqueio exige o `B-NN` tipado na sprintx (A5) e a tradução na buildx (A6); nenhuma
das duas é pré-requisito desta causa.

**O que invalidaria estas decisões:** uma verificação nova no portão (ganha linha na tabela e
posição na ordem, no script e no schema juntos — foi o que aconteceu na P0.2-C3, com a V11); a
sprintx gravar o `B-NN` com tipo — o que permitiria, em outra entrega, refinar `bloqueio_aberto`
a partir de campo tipado, nunca da prosa; ou um leitor que precise de todas as falhas, e não só
da causa — ele já tem `falhas_portao`.

## P0.2-C3 — a V11 cobra o commit da task concluída

O E1 promete, em três lugares do contrato, que a task que ficou sem commit "o E2 vai barrá-la":
quando a varredura de segredo aborta o commit, quando a branch está errada, quando o hook do
versionador recusa. A promessa não se cumpria. V1 lê `status`, V2 lê `suite`, V3 lê os testes,
V9 lê o diff — e **nenhuma** das dez cruzava `tasks.md` com `ENTREGA.commits`. Uma task podia
estar `concluida`, com suíte verde e os dois testes declarados, sem nenhuma evidência de que
alguma vez virou commit. O portão não via.

| # | Ambiguidade | Decisão tomada | Motivo |
|---|---|---|---|
| DM-117 | O que exatamente a V11 pergunta, sem virar uma segunda V1 nem uma V2 ampliada | **Uma pergunta só:** para cada task `concluida`, existe pelo menos um item de `ENTREGA.commits` com `task` **exatamente** igual ao id dela e `commit` válido? A V11 **não** lê `suite`, **não** lê `teste_integracao`/`teste_funcional` e **não** olha o status das não concluídas. Task `pendente`, `em_andamento` ou `bloqueada` **não é alvo positivo**: ela não tem commit porque não fechou, e a razão é da V1 | Falha independente e diagnosticável. Ampliar a V2 ou reaproveitar a V1 daria duas razões pelo mesmo sintoma e uma causa que não aponta para onde corrigir |
| DM-118 | `OK` ou `n/a` quando não há nenhuma task concluída | **`n/a`**, com motivo declarado — a convenção real de V1–V10, onde `n/a` é "não se aplica a este trabalho" (V4 fora de bug da runx, V5 na sprintx, V8 sem `PERFIL.md`). Havendo pelo menos uma concluída, é `OK` para o subconjunto concluído. `versionado: false` também é `n/a`: o schema já define `commits: []` sem versionador, e cobrar commit ali seria reprovar todo repositório sem versionador | `OK` sobre conjunto vazio afirmaria uma prova que ninguém produziu. `n/a` distingue "verifiquei e está certo" de "não havia o que verificar" — que é a razão de a tabela nunca omitir linha |
| DM-119 | Uma task pode aparecer mais de uma vez em `commits` (replanejamento). Quantos itens a V11 exige? | **EXISTE pelo menos um**, nunca exatamente um. Duplicidade **não** é falha da V11, e ordem e sequência dos itens também não são assunto dela. Um item malformado ao lado de um válido não estraga a prova: basta que **um** item prove | `commits` é histórico de execução, não índice de plano (`references/01-commits.md`) — um `id` reaparece legitimamente. Exigir unicidade transformaria histórico correto em falha |

Válido é o que o E1 grava: hexadecimal minúsculo de 7 a 40 caracteres, o que `git rev-parse --short HEAD` devolve | Procurar o texto do id aceitaria um item pela metade — exatamente o registro incompleto que a V11 existe para pegar. Não havia parser de `commits` a reutilizar: o leitor do `causa-do-portao.sh` lê chaves de topo escalares e não enxerga lista de mapas |

A V11 fecha a lacuna `tasks.md` ↔ `ENTREGA.commits` e para aí | Ampliar para auditoria de `git log` seria escopo novo sem exigência no contrato — e transformaria uma verificação de registro numa verificação de versionador, com falhas de natureza diferente na mesma linha |
| DM-122 | Qual `causa` uma falha V11 deriva | **Valor novo: `commit_nao_registrado`.** Nenhuma causa existente serve. `tarefa_nao_concluida` afirma que a task não está concluída, e na V11 ela **está** — quem lê iria ao `tasks.md` e não acharia nada errado. `suite_reprovada`, `teste_nao_declarado` e `regressao_nao_declarada` leem campos que a V11 nem toca. `indeterminada` é "não consegui provar", e a V11 **provou**. O valor novo passa as cinco perguntas do DM-111 | Uma causa só para V1 e V11 apagaria a diferença no ponto em que ela é acionável: `tarefa_nao_concluida` manda olhar o status da task; `commit_nao_registrado` manda olhar a lista `commits` do mesmo arquivo |
| DM-123 | Onde a `v11` entra na precedência | **Último do grupo que lê o registro da execução:** `v10`, depois `v6`–`v9`, depois `v1`–`v5` e `v11`. A isenção da V11 é por repositório, nunca por task | Criar a exceção por task exigiria um campo que nenhuma skill grava — e uma isenção que só existe em prosa é uma porta aberta para marcar qualquer task como dispensada da prova |
| DM-125 | ENTREGA histórica com task concluída sem commit | **Duas leituras separadas.** `--validar-historico` continua aceitando snapshot anterior às chaves e **não roda a V11**: nada é reescrito, nenhum commit é inventado, nenhuma causa é inferida. **Entrega ou prontidão nova roda a V11 sempre** — a inconsistência aparece e barra. O conserto é o **E1 tardio**: commita agora, acrescenta o item ao fim de `commits`, sem reordenar o histórico | Silenciar a V11 em entrega nova "por compatibilidade" devolveria exatamente o buraco que a C3 fecha. Reescrever o histórico para fazê-la passar seria maquiar — o oposto do portão |

**O que invalidaria estas decisões:** o contrato passar a exigir, em outro ponto, que o SHA de
`commits` seja provado contra o versionador (aí a V11 herda essa prova, em vez de criá-la); a
sprintx ou a runx passarem a declarar task não versionada com campo tipado (aí o DM-124 ganha o
`n/a` por task que hoje não existe); ou uma verificação futura assumir ordem e sequência de
`commits` — que é C4, e por isso a V11 não as toca.

## P0.2-C4 — `ENTREGA.commits` ganha ordem explícita e durável

O contrato dizia, em três lugares, que os itens de `commits` estão "na ordem em que fecharam" — e
essa ordem existia só na **posição física** da lista. Posição não tem identidade própria: nada
prova que ela não foi trocada, ela não distingue duas passagens da mesma task, não diz numa sessão
nova qual foi o último registro e não dá ao E1 tardio um lugar que signifique "aconteceu agora". A
C3 formalizou o E1 tardio e deixou explícito que ordem e sequência não eram assunto da V11: eram
desta entrega.

| # | Ambiguidade | Decisão tomada | Motivo |
|---|---|---|---|
| DM-126 | Como dar identidade à ordem: data, timestamp do rastro, ou campo próprio | **Campo próprio: `seq`**, inteiro positivo, monotônico e **global à ENTREGA**, gravado em todo item novo. Datas `AAAA-MM-DD` não distinguem dois fechamentos do mesmo dia; o timestamp de `docs/eventos/<trabalho_id>.jsonl` é local da máquina, append-only e **não versionado** — não é fonte canônica. A regra que fica: **datas são registro; quando há ordem contratual, existe campo de ordem** | Ordem contratual precisa ser legível de um arquivo commitado, sem depender de relógio, de fuso, de rastro local nem da memória da sessão. Nenhum dos dois candidatos sobrevive a `git show` numa máquina diferente |
| DM-127 | O que `seq` conta | A **ordem de registro do E1**, e nada mais. **Não** é número da task, número do sprint, rodada da F5, timestamp, nem quantidade de commits Git da branch. Contador **um só por ENTREGA** — nunca por task, nunca por sprint | Um contador por task devolveria o problema: duas tasks diferentes teriam `seq: 1`, e a ordem entre elas voltaria a ser a posição. O alcance global é o que torna o número comparável entre itens |
| DM-128 | Entrega antiga tem itens sem `seq`. Migrar tudo, ou conviver? | **Prefixo legado, sem migração nenhuma.** Itens sem `seq` são aceitos **só no início** da lista, com ordem efetiva pela posição (1..N), e o primeiro item moderno vale **N+1**. Depois do primeiro `seq`, **nenhum item posterior pode omiti-lo**. `[legado, legado, seq 3]` é válida; `[seq 1, legado]` e `[legado, seq 2, legado]` não. **Backfill é proibido**, inclusive "para deixar a lista uniforme" | Reescrever item antigo só para acrescentar chave é a migração em massa que o schema já proíbe (`00-schema.md`, "Regra de migração") — e mexeria em registro de commit que já está no histórico. Prefixo, e não modo, porque a exceção precisa ter fim: aceitar legado a qualquer altura seria não ter a chave |
| DM-129 | Como validar a sequência sem inventar regra para cada defeito | **Uma igualdade só: todo `seq` explícito é igual à posição do seu item** (mais "nenhum legado depois de um moderno"). Como a ordem efetiva de um item **é** a posição dele, essa comparação recusa sozinha as quatro formas de lista quebrada: duplicata, buraco, regressão e reordenação | Quatro verificações independentes divergiriam na primeira manutenção e deixariam combinações fora. Uma invariante que qualquer leitor recalcula de cabeça, e uma bancada que a prova caso a caso |
| DM-130 | O que acontece quando a sequência está quebrada — falha do portão ou violação de contrato? | **Violação de contrato do `ENTREGA.md`: PARA.** Não vira `causa` nova, não vira `indeterminada` e **não entra em `falhas_portao`**. E **nunca se conserta escolhendo outro número** | A mergex é dona da causa **observável do portão** (DM-111), e o portão lê o registro da execução — não a integridade do arquivo que o carrega. Escolher outro número para caber esconderia justamente o registro perdido que a invariante acabou de mostrar |
| DM-131 | Duas sessões podem calcular o mesmo próximo `seq` | **A C4 não resolve corrida, e não finge resolver.** Sem lock, sem seção crítica, sem ownership do índice — isso é da C5. O que a C4 garante é que o resultado de uma corrida (lista com `seq` duplicado) **seja contrato inválido e pare**, em vez de passar despercebido | Meia-solução de concorrência é pior que nenhuma: dá a impressão de exclusão mútua sem tê-la. Tornar a corrida **visível** é o que permite que a C5 a trate depois, e é o que a posição física nunca permitiu |
| DM-132 | Onde o `seq` é calculado, já que o contrato dependia de o agente editar YAML à mão | Num **escritor canônico mínimo**, `scripts/sequencia-de-commits.sh`: lê, valida, calcula o próximo e acrescenta no fim (`--ler`, `--validar`, `--proximo`, `--acrescentar`). Ele **não** reescreve item existente, **não** reordena, **não** faz backfill e mexe só na lista `commits` — `atualizado_em` continua sendo do E1. Não existia escritor executável de `commits`: o E1 mandava editar o YAML | Atribuição de ordem escrita em prosa não é testável nem determinística. Centralizar o cálculo é o mínimo para a bancada e a mutação existirem — e é o ponto onde a C5 poderá pôr a seção crítica, sem que a C4 já a implemente |
| DM-133 | A V11 passa a exigir `seq`, ou a depender de ordem? | **Não, em nenhuma das duas.** A V11 continua perguntando "existe **pelo menos um** commit válido para esta task?" sobre lista totalmente legada, moderna e mista válida; não exige `seq` em leitura histórica, não falha por sequência quebrada e não lê `seq` como quantidade de commits esperada. O que mudou é **de onde ela lê**: o parser de `commits` saiu do `prova-de-commit.sh` e virou o leitor único do `sequencia-de-commits.sh` | Dois parsers para a mesma lista divergem na primeira manutenção — e divergiram: o leitor antigo ancorava o item em `- task:` e ficava **cego** a um item que começa por `seq:`. Um leitor só; a V11 usa dele a leitura crua, porque a ordem não é pergunta dela |
| DM-134 | Onde o E1 tardio entra na série | **Sempre no próximo `seq` global, no fim da lista** — nunca "na posição lógica da task". `seq 1: T-01.01`, `seq 2: T-01.03`, `seq 3: T-01.02` é o registro correto de um E1 tardio | `seq` registra **quando o E1 aconteceu**, não a ordem numérica das tasks. Inserir no meio renumeraria itens já gravados (o que a regra proíbe) e apagaria o fato de que aquele commit só passou a existir depois — exatamente o que a chave existe para preservar |

**O que invalidaria estas decisões:** a C5 introduzir seção crítica para a atribuição do `seq` (o
cálculo continua aqui, mas passa a rodar sob exclusão mútua, e o duplicado deixa de ser desfecho
possível de corrida); um `ENTREGA.md` legado precisar ser reordenado por uma razão externa (aí o
prefixo legado deixa de bastar e a migração vira decisão própria, nunca efeito colateral de uma
gravação); ou uma verificação futura do portão passar a cobrar integridade do registro — que é o
oposto do DM-130 e precisaria de contrato próprio.

## P0.2-C5 — o índice é do E1, e o E1 não é reentrante

A C4 deu identidade à ordem de registro e fez a lista provar a própria integridade: uma corrida
entre dois E1 deixa de passar despercebida e vira contrato inválido. Faltava impedir que a corrida
aconteça. Duas execuções do E1 na mesma worktree compartilham índice, HEAD, `ENTREGA.commits` e o
próximo `seq` — e nenhum desses recursos é da task: todos são da worktree.

automática de queda virar requisito — o que precisaria de contrato próprio, porque é exatamente o
oposto do DM-141.

## P0.2-C1 — arquivo de task irmã é defeito de plano, não desvio

O contrato do E1 tinha três respostas para um arquivo que mudou: é da task, não mudou, ou é
desvio. Faltava a quarta, e ela apareceu no piloto: **mudou, não é da task que está fechando,
mas outra task da feature a declara**. Sem ela, o mesmo arquivo recebia três respostas
diferentes na mesma máquina — o `escopo-da-task.sh` perguntava pelo escopo unitário, a V9
perguntava pela união, e o `commit-por-task` chamava o caso de mistura de tasks, cujo conselho
("commite uma de cada vez") fecharia de novo uma task congelada.

Esta seção veio da branch histórica `p0.2/mergex-e1-defeito-plano` (commit `c6f1510`), integrada
à linha C3→C4→C5 na P0.2-C7-A. As decisões DM-117 a DM-123 daquela branch colidiam em número com
as da P0.2-C3 (que também partiu de DM-117): renumeradas aqui para DM-147 a DM-153, a próxima
faixa livre depois da P0.2-C5. A branch histórica permanece intacta com a numeração original; a
renumeração vale só para este documento integrado.

## P0.2-C7-B / M2 — lifecycle executável e recuperação do registro E1
